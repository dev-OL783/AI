Artefact 10: Purpose – RAG Performance Analysis
For this week’s portfolio artefact, you will conduct a systematic evaluation of the RAG pipeline from the Week 11 workshop. Your task is to assess how well the existing system works. This is the kind of evaluation that precedes any real engineering decision about which component to improve.

The analysis should be structured around a key distinction between the retrieval quality (were the right chunks retrieved for queries?) and response quality (given those chunks, did the LLM produce a good answer?). 

The RAG System
Use the LangChain + Azure RAG implementation from Activity 1 of the Week 11 workshop, with the provided knowledge base. Use the default configuration from the workshop: chunk_size=512, overlap=64, k=3, and the standard RetrievalQA chain with no custom prompt template.

Do not modify the RAG configuration before conducting your analysis — you are evaluating the baseline system. You may explore variations as part of your failure case analysis, but the main evaluation must use the default settings.

Part 1 – Performance Analysis
Design a test set composed of the questions from the workshop (below) + at least 8 additional questions covering all types below. Include at least 2 additional questions of each type.

Question type	Description	Example
Direct	The answer can be found in a single chunk of the knowledge base.	“What is the main purpose of the chunking module in a RAG pipeline?”
Synthesis	Answering requires combining information from multiple chunks or documents.	“How do hybrid search and query expansion complement each other?”
Partial	The answer may not be entirely available in the knowledge base	"What is the best chunk size for a RAG pipeline?"
Out-of-scope	The answer is not in the knowledge base. A well-behaved RAG should refuse or say it does not know.	“Who won the FIFA World Cup in 2026?”
Retrieval Performance
For each test question, run the RAG, inspect the retrieved chunks and the response, and analyse their quality. Try to compute some of the relevant metrics discussed in the lecture as averages across your full test set. Examples include:

Hit Rate — the proportion of relevant questions (not out of scope) for which at least one relevant chunk appears in the top-k retrieved results. 
Mean Precision@k — for each question, the proportion of the k retrieved chunks that are relevant; averaged over all questions. For k=3, a precision of 1.0 means all 3 retrieved chunks were relevant.
Response Quality
For each test question, rate the generated answer on at least two independent dimensions. Each dimension may use a simple three-point scale to keep the evaluation tractable. For example:

Faithfulness — does the answer rely only on the retrieved context, without adding knowledge not present in the chunks? Rate as 2 - Faithful (fully grounded), 1 - Partial (some external knowledge used), or 0 - Unfaithful (not supported by retrieved chunks).
Answer Relevance — does the answer address the question that was asked? Rate as 2 - Relevant (directly and completely answers the question), 1 - Partial (answers part of the question or is vague), or 0 - Irrelevant (does not answer the question).
Summarise both dimensions as rates across your test set (e.g. “8 out of 10 answers were Faithful = 80% Faithfulness Rate”). Present the retrieval and response results in separate tables, as shown in the submission template.

Analysis
Identify the one question your RAG handled worst, write a focused analysis of that failure, and reflect on what other aspects of a RAG system should be monitored. Your analysis should address these points:

What the answer was and why it is wrong.
Whether the failure originated in the retrieval stage (wrong chunks returned) or the generation stage (relevant chunks were returned, but the LLM still produced a poor answer). This distinction determines which module needs fixing.
One specific, actionable change to the pipeline that would address the failure. Justify why that change would help.
What other aspects of a RAG system should be monitored in real-world applications?
You should use no more than 200 words for the failure case analysis.
